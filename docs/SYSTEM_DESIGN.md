# AUTOBEST 集客システム 要件定義・システム設計

LINE公式アカウントとコーポレートサイトを「1つの集客システム」として設計する。

---

## 1. 現状

| 持っているもの | 状態 |
|---|---|
| LINE公式アカウント（bot） | 稼働。在庫カルーセル・査定申込・来店予約・問い合わせ管理 |
| 管理画面 | 稼働。在庫CRUD・写真・問い合わせ・予約・操作履歴 |
| 在庫DB | bot側に1つ（`cars` ほか15表） |
| コーポレートサイト | **未着手**（リニューアル予定） |

## 2. 課題

**集客の観点**

- LINEは「既に友だちになった人」にしか届かない。**新規の入口が無い**
- 検索から来る人（「福岡 トラック 買取」等）を受け止める場所が無い
- 在庫が外から見えないので、在庫そのものが集客に使えていない

**利用者の観点**

- 在庫を見るのに、いきなり全件が出る。**絞り込みが先に無い**
- 詳細を見るとLINEの外（Webページ）へ出てしまう。戻ってこない人が出る
- 売りたい人と買いたい人が、同じメニューの中で混ざっている

## 3. 目的と指標

**KGI**：成約数（買取・販売）

**KPI**

| 指標 | なぜ見るか |
|---|---|
| **LINE友だち追加数** | 最重要。友だちは何度でも無料で接客できる資産 |
| サイト → 友だち追加の転換率 | サイトが集客装置として働いているか |
| 在庫カルーセルの表示回数 | 在庫が見られているか |
| 査定申込数 / 来店予約数 | 商談の入口 |
| 申込のうちLINE経由の割合 | LINEが効いているか |

**この設計の中心にある考え方**

> 広告で1人集めるのに数千円かかる。一度友だちになれば、
> **reply は何通返しても無料**なので、その後の接客費用はゼロになる。
> だからサイトの役割は「売る」ことではなく、**友だちにすること**。

## 4. 全体構成

```
        検索・SNS・チラシ・看板
                 │
                 ▼
        ┌─────────────────┐
        │  コーポレートサイト   │  役割：新規の受け皿・SEO・信用の担保
        │  （静的 + 在庫API）  │
        └─────────────────┘
                 │  友だち追加（最重要の転換点）
                 ▼
        ┌─────────────────┐
        │  LINE公式アカウント   │  役割：接客・追客・再訪
        │  （reply中心／通数0） │
        └─────────────────┘
                 │
                 ▼
        ┌─────────────────┐
        │     管理画面        │  役割：在庫・問い合わせ・予約の一元管理
        └─────────────────┘
                 │
                 ▼
        ┌─────────────────┐
        │   在庫DB（1つだけ）  │  ← サイトもLINEもここを見る
        └─────────────────┘
```

**設計上の最重要判断：在庫DBは1つにする。**

店のスタッフが在庫を登録する場所は管理画面ただ1つ。
そこに入れたものが、LINEにもサイトにも自動で出る。
二重管理にすると必ず片方が古くなり、「サイトにあるのに売れてた」が起きる。

## 5. 在庫の共有（設計）

サイトはPHPを持たない静的サイトなので、**読み取り専用のJSONを吐き出す**方式にする。

```
bot側（既存）
  public/api/stock.json        公開中の在庫すべて（一覧用・軽い）
  public/api/stock/<id>.json   1台分の詳細（写真URL込み）
```

- 管理画面で在庫を保存したとき、**同時にJSONを書き出す**
  （サイトからのリクエストのたびにDBを引かない。共用サーバーの負荷を抑える）
- `status = 'published'` のものだけを書き出す。未公開が漏れない構造にする
- `Cache-Control` を短め（5分）に。`Access-Control-Allow-Origin` はサイトのドメインのみ
- 電話番号や仕入れ値など、**外に出してはいけない列を書き出さない**
  （書き出す列を明示的に列挙する。`SELECT *` を使わない）

サイト側はこのJSONを読んで在庫一覧・詳細を描く。
JSONが取れないときは「在庫はLINEでご覧いただけます」に差し替える。

## 6. 利用者の動線

**A. 検索から来た人（新規）**

```
「福岡 トラック 買取」で検索
  → サイトの /purchase/truck/
  → 「他店で断られた車も買います」で納得
  → ①LINEで査定（推奨）  ②Webフォームで査定  ③電話
```

LINEを一番大きく置く。理由は「アプリを入れずに済む」「あとで店から連絡できる」。

**B. 在庫を探しに来た人**

```
サイトの在庫一覧 → 気になる車 → 「LINEで問い合わせる」
  → 友だち追加 → その車の詳細がLINEに出る
```

**車両IDを引き継いで友だち追加する**のが肝。
追加した直後に「お問い合わせの車両はこちらです」と出れば、会話が始まる。

**C. すでに友だちの人**

```
リッチメニュー → 絞り込み → カルーセル → 詳細 → 予約
```

全部LINEの中で完結する。外に出さない。

## 7. LINE側の新要件

### 7-1. 在庫閲覧を「絞り込んでから」に変える

**現状**：「販売在庫を探す」を押すと、いきなり全件のカルーセルが出る。
**課題**：乗用車を探している人に重機が混ざる。逆も同じ。

**変更後の流れ（2段階。それ以上は増やさない）**

```
① 「どんなお車をお探しですか？」
     [乗用車・軽] [トラック・バス] [重機・作業車] [その他] [すべて見る]

② 「ご希望の拠点はありますか？」
     [福岡本社] [神奈川支店] [どちらでも]

③ カルーセル（該当N台）
```

- **各段階に必ず逃げ道を置く**（「すべて見る」「どちらでも」）。
  3回以上聞くと離脱するので、2回で打ち切る
- 選んだ条件は、そのまま**新着通知の条件として保存するか聞く**
  （「この条件で新着が入ったらお知らせしますか？」）。
  絞り込みと通知設定が別々の作業になっているのを1つにまとめる
- 予算の絞り込みは②には入れない。カルーセルの下にクイックリプライで出す
  （最初に予算を聞くと答えづらく、離脱する）

### 7-2. 詳細をLINEのメッセージで返す

**現状**：カルーセルの「詳細を見る」がWebページを開く。
**課題**：LINEの外に出ると戻ってこない人が出る。

**変更後**

「詳細を見る」を postback にして、**Flexメッセージで詳細を返す**。

```
┌──────────────────────┐
│  [ 大きい写真 1枚 ]        │
│  新着  在庫番号 FK-20641   │
│  トヨタ ハイエースバン      │
│  スーパーGL ダークプライムII │
│                          │
│  支払総額   328.0万円      │
│  車両本体   298.0万円      │
│  ─────────────────       │
│  年式      2021年          │
│  走行距離   4.8万km        │
│  車検      2027年3月       │
│  ミッション  AT            │
│  拠点      福岡本社        │
│                          │
│ [写真をすべて見る（4枚）]   │ → Webページ（写真が主目的の人だけ外に出す）
│ [来店・商談を予約する]      │
│ [お気に入りに追加]         │
└──────────────────────┘
```

- **reply なので通数は消費しない**
- 重機は走行距離ではなく稼働時間を出す。価格未定は「価格応談」
- 写真を複数見たい人だけWebへ。それ以外はLINEの中で完結する
- 非公開・売却済みになっていたら「掲載が終了しました」を返す
  （URLを知られても未公開在庫が見えない構造は既にあるので、それを踏襲）

### 7-3. サイトから来た人を受け止める

友だち追加リンクに車両IDを載せる。

```
サイト：https://line.me/R/ti/p/@xxxx?liff.state=car_12
追加直後：あいさつ ＋ その車両の詳細カード
```

LINEの「友だち追加時のあいさつメッセージ」は**通数を消費しない**ので、
ここで在庫の詳細まで見せてしまってよい。

## 8. データ設計（差分）

既存15表はそのまま使う。追加は最小限。

**追加する列**

```
line_users
  + entry_source   TEXT NULL   どこから友だちになったか（site_stock / site_purchase / qr_store …）
  + entry_car_id   INT  NULL   サイトのどの車両から来たか
```

流入元が分かると「サイトのどのページが友だちを連れてきたか」が数えられる。
広告や看板にQRを出すときも、別の値を付ければ効果が比較できる。

**追加する表**

```
search_sessions   絞り込みの途中経過（誰が何を選んだか）
  id / line_user_id / category / location / price_max / step / created_at
```

2段階の絞り込みは「①を選んだ状態で②を聞く」ので、途中の状態を持つ必要がある。
postbackのdataに全部載せる手もあるが、条件が増えると上限（300文字）に当たる。

**既存の表で足りるもの**

- 検索結果の表示回数 → `audit_logs` に `action='stock.view'` で積む
- 新着通知の条件 → `notification_conditions` をそのまま使う

## 9. 非機能要件

| 項目 | 要件 | 理由 |
|---|---|---|
| Webhook応答 | 3秒以内に200 | LINEが再送してくる |
| 在庫JSON生成 | 保存時に書き出し | 参照のたびにDBを引かない |
| LINE通数 | **push/multicast/broadcastを増やさない** | 無料枠は月200通 |
| サイト表示 | Lighthouseモバイル90以上 | 検索順位と離脱率に直結 |
| 未公開在庫 | LINE・サイト・JSONのどこからも見えない | 商談中・売却済みの漏洩は信用問題 |
| 個人情報 | 査定写真は公開領域に置かない | 既存の方式を踏襲 |

## 10. 計測

**サイト側**：Google Analytics 4 + Search Console

**LINE側**：`audit_logs` に積む（既存の表を使う）

```
stock.search      絞り込みで何が選ばれたか（カテゴリ・拠点の分布）
stock.view        カルーセルが表示された
car.detail        詳細が開かれた（どの車が人気か）
inquiry.create    査定申込
reservation.create 来店予約
```

**毎月見る数字**

- 友だち追加数と、その流入元の内訳
- 詳細まで見られた車両の上位10台（仕入れの判断材料になる）
- 絞り込みで選ばれた区分の分布（どの層が来ているか）
- 申込数のうちLINE経由の割合

## 11. 実装の順序

前の段が次の段の土台になるので、この順で進める。

| 段 | やること | なぜこの順か |
|---|---|---|
| 1 | LINEの在庫閲覧を改善（7-1・7-2） | サイトが無くても今日から効果が出る |
| 2 | 在庫JSONの書き出し（5節） | サイトを作る前に用意が要る |
| 3 | サイトの共通部品とトップ | ここから新規流入が始まる |
| 4 | サイトの買取ページ群 | 検索流入の主力 |
| 5 | サイトの在庫ページ（2のJSONを読む） | 在庫を集客に使う |
| 6 | 流入元の計測（8節） | 3〜5が動いてから意味を持つ |
| 7 | 数字を見て改善 | — |

**1を先にやる理由**：サイトは作ってから効果が出るまで数か月かかる。
LINEの改善は既にいる友だちに今日から効く。

## 12. 決めてから着手すること

1. **在庫JSONを出してよいか**（= サイトに在庫を載せるか）。
   載せないなら5・7-3・9が変わる
2. サイトのドメインとサーバー（既存のautobest.jpを差し替えるのか、並行して作るのか）
3. 取材シート（`docs/WEBSITE_PROMPT.md`）が埋まるか。
   埋まらないとサイトは公開できない
