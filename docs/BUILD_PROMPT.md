# 中古車販売店のLINE公式アカウント — 一式を作るためのプロンプト

Codexなどの実装担当に丸ごと渡すための仕様。
**この文書だけで作り切れる**ことを狙って書いてある。

UIの見た目は `docs/UI_PROMPT.md` に分けてある（配色の16進と8画面の中身）。
本文からも要点は引いてあるので、まずこちらを読んでから必要に応じて見ればよい。

---

## プロンプト本文（ここから下をコピー）

中古車の買取・販売店のLINE公式アカウント一式を作ってください。
お客様はLINEのトークから在庫を探し、査定を申し込み、来店を予約できます。
店側は管理画面から在庫と問い合わせを扱います。

### 0. 先に読むこと：外せない制約

**動作環境はエックスサーバーの共用レンタルサーバー。** ここが設計のほぼ全てを決める。

| 制約 | 結果 |
|---|---|
| Composerが使えない | 外部ライブラリを一切使わない。HTTPは素の`curl`、オートローダは自前 |
| 常駐プロセスを立てられない | 非同期処理は「DBのキュー表 + cron」で作る。ワーカーやデーモンは不可 |
| PHPの実行時間に上限 | 長い処理は1回のcronで終わらせず、件数と秒数で必ず打ち切って次に回す |
| DBホストが`localhost`ではない | `mysqlXXX.xserver.jp` 形式。設定で指定できるようにする |
| WAFが管理画面のPOSTを誤検知する | 防御をアプリ側で完結させる（署名検証・プリペアドステートメント・出力エスケープ） |
| **LINEは無料プラン（月200通）** | **通数に入るのは push / multicast / broadcast だけ。reply は無料** |

最後の1行が機能設計を決める。**お客様の操作に返す（reply）形で作れば通数を消費しない。**
自動配信を足したくなったら、必ず先に通数の見積もりを出すこと。
友だち100人に月2回の通知は400通で、その月は査定の返信すら送れなくなる。

言語はPHP 8.2以上。DBはMySQL（utf8mb4）を本番想定とするが、
**MySQLとSQLiteの両方で動く**ようにする（MySQLをまだ用意できない環境があるため）。

### 1. データモデル

15の表を作る。時刻はすべてJST。

| 表 | 役割 |
|---|---|
| `line_users` | 友だち。LINEのuserId、表示名、ブロック状態 |
| `admin_users` | 管理画面のログイン。パスワードは`password_hash()`、失敗回数とロック時刻 |
| `cars` | 販売在庫。後述 |
| `car_images` | 在庫写真。URLと並び順 |
| `purchase_records` | 買取実績。公開/非公開 |
| `inquiries` | 問い合わせ（査定申込・在庫問い合わせ・来店相談） |
| `inquiry_notes` | 対応履歴。「電話した」「見積を送った」を時系列で積む |
| `inquiry_images` | 査定写真。**ファイル名だけ**を持つ（実体は公開領域の外） |
| `reservations` | 来店・商談予約。第1〜第3希望と確定日時 |
| `favorites` | お気に入り（LINEユーザー × 車両） |
| `notification_conditions` | 新着のお知らせ条件（1人1件で運用） |
| `notification_log` | その人に見せた車両。同じ車を毎回出さないため |
| `message_queue` | 非同期処理のキュー |
| `webhook_events` | 受信済みイベントID。重複配信の無視に使う |
| `audit_logs` | 管理操作の証跡 |

`cars` の主な列:

```
stock_number（店舗の在庫番号・一意）
category      passenger | truck | machinery | other
location      fukuoka | kanagawa
maker, model_name, grade, model_year
mileage_km          走行距離
engine_hours        稼働時間（重機用。走行距離の代わりに出す）
total_price         支払総額
body_price          車両本体価格
price_negotiable    1なら「価格応談」（金額未定）
inspection_until, body_color, fuel, transmission, body_type, note
status        draft | pending | published | negotiating | sold
sort_order, published_at
```

`inquiries` と `reservations` は **LINE経由でもWebフォーム経由でも受けられる**ようにする。
`line_user_id` はNULL可にし、`source`（line/web/liff）と
`contact_name` / `contact_tel` / `contact_email` を持たせる。
担当者（`assigned_admin_id`）も持つ。

**LINEユーザーの行を消しても問い合わせ履歴は残す**（外部キーはCASCADEではなくSET NULL）。
消えるとトラブル対応で「言った・言わない」を確認できなくなる。

既存DBに列を足していけるよう、**移行の仕組み**も作る。
`sql/migrations/NNN_名前_{mysql|sqlite}.sql` を番号順に適用し、適用済みを表に記録する。
新規インストールには「実行せず適用済みとして記録する」モードを用意する
（`sql/schema.sql` は常に最新の形なので、移行を流すと「列が既にある」で落ちる）。

### 2. LINE bot（reply駆動）

**Webhookの受け口**

- 署名（`X-Line-Signature`）をHMAC-SHA256で検証する。**生のリクエストボディで**行い、
  比較は`hash_equals()`。不一致なら403
- 検証を通ったら**先に200を返してから**中身を処理する
  （3秒以内に返さないとLINEが再送してくる）
- 同じイベントIDを二度処理しない（`webhook_events`にUNIQUEで入れ、
  挿入できた時だけ処理する）
- LINEの「検証」ボタンはダミーのreplyToken（ゼロ埋め）を送ってくる。返信してはいけない

**リッチメニュー（2500 × 1686px、3タブ）**

上部にタブ3つ、下に3列×2行の6ボタン。タブ切替はリッチメニューエイリアスで行う。

```
タブA 車を探す   販売在庫を探す / 条件から検索 / 新着入庫 /
                 お気に入り / 来店・商談予約 / 福岡・神奈川の店舗
タブB 車を売る   無料買取査定 / 高額査定実績 / 高額査定の理由 /
                 買取までの流れ / 必要書類 / 査定について相談
タブC サポート   よくある質問 / 問い合わせ / 予約確認 /
                 通知設定 / 会社・店舗案内 / Webサイト
```

タブ切替もpostbackとして飛んでくる。**返信してはいけない**
（押すたびにトークが埋まる）。切替のpostbackだけ早期returnで無視する。

**在庫カルーセル（Flex Message）**

- 1回10台＋「もっと見る」で最大11バブル（上限は12）
- 各カードに 写真・新着バッジ・車名・年式/走行距離・価格・拠点・「詳細を見る」
- **写真が無い車両でも新着バッジが出ること**（バッジを写真の上にだけ重ねると消える）
- 重機は走行距離ではなく稼働時間を出す
- `price_negotiable` の車両は金額ではなく「価格応談」と出す
- 価格は万円表記に統一する（詳細ページと食い違わせない）
- 絞り込み（カテゴリ・拠点・並び順）を次ページのpostbackに引き継ぐ
- **公開中（`status = 'published'`）以外は絶対に出さない**

**キーワード応答**

入力の表記ゆれを吸収してから判定する。半角カナ・全角英数・カタカナを正規化する。
`mb_convert_kana()` は**モードを重ねても連鎖しない**ので、
「半角カナ→全角カナ」と「カタカナ→ひらがな」を2回に分けて呼ぶこと。

正規化でひらがなに寄せるなら、**キーワード側はひらがなか漢字で書く**。
カタカナで書くと永久に一致しない条件になる。

拾う語の例:

```
査定・買取・売りたい・見積          → 査定の案内 ＋ 申込フォームのボタン
在庫・販売・探し・車を見            → 在庫カルーセル
トラック・ダンプ・バス              → トラックで絞ったカルーセル
重機・ユンボ・フォークリフト        → 重機で絞ったカルーセル
福岡 / 神奈川・横浜                 → 拠点で絞る
新着・入荷                          → その人向けの新着（後述）
通知・お知らせ                      → 通知設定
営業・時間・定休・場所・住所        → 店舗情報
電話・連絡                          → 電話番号
お気に入り                          → お気に入り一覧
それ以外                            → 担当者が確認して返信する旨
```

**「新着」は在庫より先に判定する。** 後ろに置くと「新着在庫ある？」が
「在庫」に先に拾われ、条件付きの新着が出せない。

**新着のお知らせ（通数を使わない方式）**

自動配信にしない。条件を覚えておき、**押されたときにその人向けの新着を返す**。

- 通知設定の画面で、クイックリプライから車種・拠点・予算を選ばせる（LIFF不要）
- 「新着入庫」を押すと、条件に合う**まだ見せていない**車両を返す
- 見せた車両は `notification_log` に記録し、次から除外する
- 期間は直近60日で区切る（これが無いと初回に在庫全部が「新着」になる）
- **条件が未設定の人には記録しない。** 押すたび内容が変わると
  「さっき見た車が消えた」になるので、未設定のうちは全体の新着一覧のまま
- 該当が無くなったら「いまのところ新着はありません」＋条件変更の導線を返す

**お気に入り**

車両詳細から登録。二重登録はDBのUNIQUE制約に任せる。
非公開になった車両は登録させず、「掲載が終了しました」と返す。

### 3. 公開フォーム（LIFFを使わない素のWebページ）

**LIFFにしない理由**：LINEログインチャネルが無くても今日から受け付けられ、
店頭のQRコードやWebサイトからも同じURLが使えるため。
LINEと紐づける口だけ用意しておき、設定が入った時点で自動的に効くようにする。

**査定申込フォーム**

必須は「お名前・電話番号・メーカー・車種」の4つだけにする。
年式や走行距離まで必須にすると、うろ覚えの人がそこで離脱する。
足りない情報は折り返しの電話で埋める方が、申込自体を取りこぼさない。

写真は任意で最大8枚（外装4面・内装・メーター程度）。

**来店・商談予約フォーム**

第1希望のみ必須、第2・第3は任意。拠点と目的（来店/オンライン相談）を選ぶ。
車両詳細から `?car_id=` 付きで開かれたら、その車両を対象として表示する。
**送信時点では必ず仮予約。** 確定は管理画面で人が行う
（在庫状況と担当者の在席を人が見る必要がある）。

**迷惑送信への構え（3枚重ね）**

| 仕組み | 内容 |
|---|---|
| ハニーポット | 人には見えない入力欄。自動投稿は素直に埋めてくる |
| 経過時間 | 表示から3秒未満／1時間超の送信を拒否。発行時刻はHMACで署名して改ざんを防ぐ |
| 連投制限 | 同じIPから1時間あたり5件まで |

**CAPTCHAは入れない。** 外部スクリプトを読むとWAFやLINE内ブラウザで
表示が崩れることがあり、来店予約を取りこぼす方が損失が大きい。

送信が通ったらトークンを作り直す（戻るボタンでの二重登録を防ぐ）。
送信後は必ずリダイレクトする（POST→リダイレクト→GET）。

### 4. 管理画面

ログインは自前（`password_hash`、試行回数の上限とロック、無操作タイムアウト、
ログイン時のセッションID再生成）。更新系のPOSTは全てCSRFトークンを検証する。

| 画面 | 内容 |
|---|---|
| 販売在庫 | 一覧・絞り込み・状態変更・削除 |
| 在庫の編集 | 全項目の入力と検証、写真のアップロード・並べ替え・削除 |
| 買取実績 | 登録・編集・公開/非公開 |
| 問い合わせ一覧 | 状態・種別・担当で絞り込み、担当者と状態の変更 |
| 問い合わせ詳細 | 申込内容、**査定写真の表示**、担当者、状態、対応履歴の追加 |
| 予約 | これから来る予約を早い順に。希望日時から「これで確定」、状態変更、担当者、メモ |
| 操作履歴 | 誰がいつ何を変えたか。**削除する口を作らない** |

**査定写真の扱いがこの機能の要。**
在庫写真と違い、これは**お客様の車の写真＝個人情報**。公開領域には置かない。

```
実体  storage/assessments/{問い合わせID}/{乱数32桁}.jpg （パーミッション600）
DB    ファイル名だけ。パスもURLも持たない
配信  管理画面のログイン必須スクリプトだけ
```

- 未ログインは403ではなく**404**（そこに何かある、と教えない）
- 問い合わせを削除したら実体も消す（消し忘れると個人情報が残り続ける）
- 置き場所に`.htaccess`で全面拒否を置く
  （サブディレクトリ設置ではリポジトリごと公開領域の下に入る可能性があるため）

**画像アップロードは管理画面で最も危険な機能。** 次を必ず通す。

1. `is_uploaded_file()` で確認（パスを細工されて任意のファイルを扱わされるのを防ぐ）
2. サイズ上限
3. **拡張子ではなく中身**で判定（`finfo` + `getimagesize`）
4. ファイル名は元の名前を一切使わず乱数で作り直す
5. 長辺1600pxに縮小
6. 保存先でPHPが実行されないよう`.htaccess`を置く

**管理ユーザーを画面から作れるようにしない。**
そこを乗っ取られると攻撃者が正規の入口を作れる。作成はCLIだけにする。

### 5. cronバッチ

**キュー処理**

`message_queue` から`pending`を拾って処理する。cronで1分ごとに叩く。

1. **多重起動を防ぐ**（`flock`）。cronは前回が終わる前でも次を起動する
2. **1回の実行に上限**（件数と経過時間の両方。例：50件または50秒）
3. **`processing`のまま放置された行を拾い直す**（一定時間より古いものを`pending`に戻す）
4. **リトライは回数上限つきの指数バックオフ。**
   429と5xxだけ再試行し、4xxは何度送っても通らないので即失敗にする。
   上限に達したら理由を残して`failed`にする。**黙って消さない**
5. 二重送信防止に `X-Line-Retry-Key` を使う（リトライでは同じキーを送る）

**通数の歯止め（これが一番大事）**

送信前に残り通数を確認する。

```
GET /v2/bot/message/quota              → {"type":"limited","value":200}
GET /v2/bot/message/quota/consumption  → {"totalUsage":123}
```

- 消費見込みが残量を超えるなら**送らずに`pending`のまま次回へ回す**
  （`failed`にしない。枠が戻る翌月に送れる）
- 残量の取得はcron 1回につき1度でよい。送った分は手元で引く
- **APIが取れなかったら送らない側に倒す。** 数えられないまま送るのが一番まずい
- 止めたことはログに残す

**一斉配信**は「キューに積むだけ」にする（その場で送ると時間切れになる）。
`multicast`は1リクエスト500件までなので、宛先を500人ずつに割ってから積む。
管理画面から送るなら、積む前に「この配信で◯通消費します。残りは◯通です」を見せる。

### 7. 実装の約束事

- **コメントは日本語で「なぜそうしたか」を書く。** 何をしているかはコードを読めば分かる
- 出力は必ずHTMLエスケープを通す（`htmlspecialchars($x, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8')`）
- SQLは必ずプリペアドステートメント。値を文字列連結でSQLに入れない
- **並び順やカラム名にユーザー入力を使わない。** 許可した文字列にしか分岐しない
- 例外を握りつぶさない。ログに残し、利用者には状況が分かる日本語を返す
- 選択肢の定数は1か所を正とする（画面とDBでずれるのを防ぐ）
- **1ファイル1クラス**（自前オートローダがクラス名でファイルを探すため）

### 8. 踏みやすい落とし穴

**DB**

- `LIMIT ?` は使えない（エミュレーションを切ると文字列としてバインドされ構文エラー）。
  `(int)`にキャストして埋め込む専用のヘルパを用意する
- **SQLiteの`CURRENT_TIMESTAMP`はUTC。** アプリがJSTで書くと同じ表の中で9時間ずれる。
  既定値もトリガも `datetime('now','+9 hours')` に揃える
- 書き分けが要るもの：`INSERT IGNORE`↔`INSERT OR IGNORE`、
  `ON DUPLICATE KEY UPDATE`↔`ON CONFLICT DO UPDATE`、`NOW()`↔`datetime(...)`
- **LIKEのエスケープ文字にバックスラッシュを使わない。**
  SQL文字列中の扱いがMySQLとSQLiteで違う（1文字 vs 2文字）。`ESCAPE '!'` にする
- **空文字をDATETIME列に入れない。** MySQLは1292で拒否、SQLiteは黙って空文字を保存する。
  未入力は必ずNULL
- SQLiteは列のNULL可・CHECK制約を後から変えられない。表を作り直して詰め替える。
  **表をDROPするとトリガも消えるので張り直す**

**PHP**

- **`trim()`の第2引数はバイト単位で削る。** 全角スペース（U+3000 = `E3 80 80`）を
  削り文字に渡すと「トヨタ」の先頭バイトまで削れて文字化けする。
  文字単位で扱うなら `preg_replace('/\A[\s\x{3000}]+|[\s\x{3000}]+\z/u', '', $s)`
- 壊れたUTF-8が1バイトでも混ざると `json_encode()` は `false` を返す。
  上の文字化けと組み合わさると、申込内容がまるごと空で保存される
- **セッションはHTMLを1文字でも出す前に開始する。** 出力後だと`Set-Cookie`が飛ばず、
  **全ての送信がCSRFで弾かれる**
- `isset()`では「空文字」と「未送信」を区別できない（`parse_str`は空文字を作る）。
  「指定を外す」を扱うなら`array_key_exists()`
- 配列の`+`は**左側の値を優先する**。整形済みの値を残したいなら順序に注意

**Webhook**

- Webhookは既に200を返し終えているので、失敗時に`header()`を呼んでも意味がなく、
  `exit`は**残りのイベントの処理を巻き込んで止める**。必ず例外を投げる

### 9. 完成の定義

**テストを一緒に作る。** 1コマンドで走り、DBの作り直しから
ビルトインサーバの起動までやるものにする。

最低限これを確かめる:

- 署名検証（正しい署名を受理／改ざん・別シークレット・署名なしを拒否）
- 同じイベントを二度処理しない
- キーワード応答（半角カナ・全角・濁点付きを含む）
- 在庫カルーセルのページング、絞り込みの引き継ぎ
- **未公開の在庫がLINEにもWebにも漏れないこと**

- 査定写真が未ログインで取れないこと、削除で実体も消えること
